수정 시각이 같은 상품 120개를 100개씩 읽으면, 나머지 20개는?

realbong2024.06.16수정 2026.11.19
spring-batchmybatispostgresql

수정 시각이 같은 상품을 빠뜨리거나 중복하지 않도록 updated_at과 id를 함께 기억하는 복합 키셋 페이징.

목차

  • ‘10시까지’와 ‘10시의 1100번까지’
  • 마치며
  • 레퍼런스

낚시용품 쇼핑몰에서 오전 10시 정각에 상품 120개의 가격을 한꺼번에 바꿨다. 상품 ID는 1001번부터 1120번까지다. 이 120개를 가격비교 사이트에 수정된 순서대로 보내려고 한다. 두 페이지를 읽는 동안 추가 변경은 없다고 해보자.

updated_at은 상품이 마지막으로 수정된 시각이다. 첫 조회는 ORDER BY updated_at, id LIMIT 100으로 했다. 수정 시각이 같으면 ID가 작은 상품부터 읽으니 첫 페이지의 마지막 상품은 10:00에 수정한 1100번이다. 여기서 ‘10시까지 읽었다’고 기억하면 어떻게 될까?

다음 쿼리에 WHERE updated_at > #{lastUpdatedAt}을 넣으면 두 번째 조회 결과는 0개다. 11011120번은 아직 보내지도 않았는데 수정 시각이 똑같이 10:00이라서 빠진다. 반대로 >=로 바꾸면 10시 상품 전체가 다시 후보가 된다. 같은 정렬 순서로 100개를 고르니 방금 보낸 10011100번이 그대로 나온다.

‘10시까지’와 ‘10시의 1100번까지’

정렬할 때는 시각이 같으면 ID까지 봤는데, 읽은 위치를 기록할 때는 시각만 남겼다. 그래서 배치가 첫 페이지의 마지막 상품에서 updated_at과 id를 둘 다 기억하고 다음 조회 때 MyBatis 매퍼에 넘기도록 했다.

SELECT id, updated_at
FROM product
WHERE (updated_at, id) > (#{lastUpdatedAt}, #{lastId})
ORDER BY updated_at, id
LIMIT 100

PostgreSQL은 괄호 안의 값을 왼쪽부터 비교한다. 이번에는 수정 시각이 전부 같으니 두 번째 값인 ID에서 순서가 갈린다. (10:00, 1100) 다음에 오는 상품은 1101번부터 1120번까지, 정확히 20개다.

첫 페이지의 마지막 상품은 같다. 그 상품에서 어떤 값을 기억했는지에 따라 두 번째 페이지가 달라진다.

PAGE 1     [1001 ........ 1100]   [1101 .... 1120]
            <--- 100 read --->     <-- 20 left -->
                             |
                             v
PAGE 2     last row: (10:00, 1100)
             |
             +-- time >  10:00      -> []           0 rows
             +-- time >= 10:00      -> [1001..1100]  same 100 rows
             `-- (time, id) > last  -> [1101..1120]  final 20

마치며

상품을 ID 순으로 보낸다면 ‘1100번까지 보냈다’는 기록으로 다음 페이지를 찾을 수 있다. 이번 배치에서 남겨야 할 메모는 ‘10시에 수정된 상품 중 1100번까지 보냈다’다. 이렇게 두 값을 함께 다음 페이지의 기준으로 쓰는 게 복합 키셋 페이징이다. 첫 페이지에서 100개, 다음 페이지에서 남은 20개를 읽으면 120개를 빠짐없이 보낸 셈이다.
