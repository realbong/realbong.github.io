상품 10만 개를 SELECT 한 번으로 읽으면 메모리에 다 올라갈까?

realbong2024.06.09수정 2026.11.19
spring-batchmybatispostgresql

selectList와 selectCursor의 차이, PostgreSQL JDBC의 fetchSize와 자동 커밋 조건을 상품 CSV 예제로 살펴본다.

새벽마다 낚시용품 쇼핑몰의 판매 상품을 CSV 파일로 만들어 가격비교 사이트에 보냈다. 어느 날 아침, 파일은 제시간에 나왔는데 같은 서버에서 돌던 재고 집계가 평소보다 늦게 끝나 있었다. 두 배치는 각각 쿠버네티스 CronJob에 등록돼 있어 매일 새벽 정해진 시각에 자동으로 시작한다. 그날은 두 배치가 한동안 같은 서버에서 별도의 자바 프로세스로 돌았다.

처음엔 재고 집계 코드부터 봤다. 그러다 실행 시간이 겹친 CSV 배치도 열어 봤다. 파일이 제시간에 나왔더라도 그동안 서버 자원을 얼마나 썼는지는 별개였다.

파일에는 상품을 한 줄씩 쓰면서, 정작 첫 줄을 쓰기 전에 selectList()로 상품 10만 개를 전부 가져오고 있었다. 파일을 절반쯤 썼을 때도 이미 써 버린 5만 개가 리스트에 그대로 남아 있었다. 재고 집계가 늦어진 이유까지 이것 하나로 설명할 수는 없었다. 그래도 CSV를 만드는 동안 이 리스트를 끝까지 들고 있을 이유는 없었다.

SQL은 지금처럼 한 번만 실행하되, 첫 상품을 받아 오는 대로 CSV에 쓸 수 있을까? 데이터베이스에서 조회 결과의 현재 위치를 기억하고 다음 행으로 이동하며 읽는 방식을 커서(cursor)라고 한다. 자바에서는 MyBatis의 selectCursor()가 돌려주는 Cursor<Product>로 그 결과를 차례로 읽을 수 있다.

10만 개 대신 구멍찌(101), 목줄(103), 두레박(104), 바늘 빼기(105) 네 개로 줄여 보자. 아래 MyBatis 매퍼는 PostgreSQL에서 판매 상품을 ID 순으로 조회한다.

<mapper namespace="ProductMapper">
  <select id="selectOnSale" resultType="example.Product"
          fetchSize="2" resultSetType="FORWARD_ONLY">
    SELECT id, name, price
    FROM product
    WHERE status = 'ON_SALE'
    ORDER BY id
  </select>
</mapper>

아래 예시는 조회에 쓰는 연결에서 자동 커밋을 꺼 둔 경우다. 그래야 PostgreSQL JDBC 드라이버가 결과를 여러 번에 나눠 받을 수 있다.

  • fetchSize="2"는 드라이버에 한 번에 두 행씩 받아 달라는 뜻이다. PostgreSQL에서 커서 조회 조건을 갖추면 처음에 구멍찌·목줄을 받고, 세 번째 상품이 필요할 때 두레박·바늘 빼기를 받는다. 네 상품을 모두 읽는다. 여기에 SQL로 LIMIT 2를 썼다면 조회 결과 자체가 두 상품에서 끝난다.
  • resultSetType="FORWARD_ONLY"는 결과를 앞으로만 읽겠다는 뜻이다. 구멍찌에서 목줄로 넘어간 뒤 같은 결과에서 이전 행으로 되감지 않는다. 상품의 순서는 SQL의 ORDER BY id가 정한다.

같은 매퍼를 자바에서 호출하는 두 가지 방법이다. 각각 열린 MyBatis 세션 안에서 실행한다고 보면 된다.

// 리스트로 받으면 전체 상품이 모인 뒤에 첫 줄을 쓴다.
List<Product> products = session.selectList("ProductMapper.selectOnSale");
for (Product product : products) {
    writeCsvRow(product);
}
// 커서는 결과를 순서대로 꺼내면서 한 줄씩 쓸 수 있다.
try (Cursor<Product> products = session.selectCursor("ProductMapper.selectOnSale")) {
    for (Product product : products) {
        writeCsvRow(product);
    }
}

Spring Batch에서는 누가 커서를 열까?

Step에서 이 매퍼를 쓰려면 MyBatis-Spring의 Reader에 쿼리 ID를 알려준다. 위의 자바 반복문을 Step에 따로 작성할 필요는 없다.

@Bean
MyBatisCursorItemReader<Product> productReader(SqlSessionFactory factory) {
    return new MyBatisCursorItemReaderBuilder<Product>()
            .sqlSessionFactory(factory)
            .queryId("ProductMapper.selectOnSale")
            .build();
}

Step이 Reader를 열면 Reader가 MyBatis의 selectCursor()를 호출한다. 첫 번째 read()는 구멍찌(101), 두 번째는 목줄(103)을 돌려준다. 세 번째 상품을 읽을 때를 보면 read()와 DB 왕복의 차이가 보인다. 그림의 숫자는 상품 ID다.

Step        Reader / MyBatis        JDBC driver           PostgreSQL
 |-- open() ----->|--- selectCursor --->|--- SELECT once ----->|
 |                |                     |<----- [101,103] -----|
 |-- read() ----->|--- next() --------->|                      |
 |<----- 101 -----|<------ 101 ---------|                      |
 |-- read() ----->|--- next() --------->|                      |
 |<----- 103 -----|<------ 103 ---------|                      |
 |-- read() ----->|--- next() --------->|--- fetch next 2 ---->|
 |<----- 104 -----|<------ 104 ---------|<----- [104,105] -----|
 |-- read() ----->|--- next() --------->|                      |
 |<----- 105 -----|<------ 105 ---------|                      |

두레박을 꺼낼 때 DB와 다시 통신하지만 새 SELECT를 실행하지는 않는다. 처음 열어 둔 결과에서 다음 두 행을 가져오므로 Reader는 커서를 닫을 때까지 DB 연결을 쓴다.

여기서 Reader와 드라이버를 구분해야 한다. Reader가 상품을 하나씩 건네도 PostgreSQL JDBC 드라이버는 기본 설정에서 결과 전체를 받아 둔다. 매퍼의 fetchSize와 조회 연결의 자동 커밋 설정까지 살펴본 이유다.

마치며

CSV에 101번째 상품을 쓸 때 첫 번째 상품은 어디에 있어야 할까? 파일에 첫 줄로 남아 있으면 충분하다. selectList()로 받으면 그 첫 상품도 여전히 리스트에 들어 있다. 커서로 읽고 JDBC 드라이버도 결과를 나눠 받도록 설정하면, 이미 쓴 상품은 붙들어 두지 않고 다음 묶음을 받아 쓸 수 있다.

새벽에 재고 집계가 늦어진 원인까지 이걸로 밝혀낸 건 아니다. 그래도 CSV 코드에서 무엇을 줄일 수 있는지는 분명해졌다. 파일에는 10만 줄이 필요하지만, 그 파일을 만드는 JVM에 상품 10만 개가 한꺼번에 있을 필요는 없다.
