Spring Batch에서 100개씩 읽는데 왜 뒤로 갈수록 느려질까?

realbong2024.06.02수정 2026.11.19
spring-batchmybatispostgresql

MyBatisPagingItemReader의 pageSize와 OFFSET을 따라가며 뒤쪽 페이지가 느려지는 이유와 키셋 페이징을 살펴본다.

목차

  • Reader에서 페이지 크기를 정했는데 매퍼에도 OFFSET을 써야 할까?
  • 첫 페이지를 읽고 나서 구멍찌 판매가 끝나면?
  • 마지막 100개를 읽기까지
  • 마치며
  • 레퍼런스

낚시용품 쇼핑몰에서 매일 밤 가격비교 사이트에 상품 목록을 보낸다. Spring Batch로 판매 중인 상품을 ID 순서대로 100개씩 읽고, 상품명과 가격을 CSV 파일에 한 줄씩 쓴다. 오늘 보낼 상품은 10만 개다. 첫 100개는 금방 읽히는데 끝으로 갈수록 다음 100개를 기다리는 시간이 길어진다. 상품을 읽는 Reader에는 처음부터 끝까지 100개씩 가져오라고 했는데 왜 그럴까?

쿼리를 눈으로 따라갈 수 있게 잠깐 두 개씩만 읽어 보자. 아래 다섯 상품 가운데 지금 팔고 있는 건 네 개다. 첫 두 개를 읽고 나면 다음 쿼리는 어디서부터 읽어야 할까?

이럴 때 쓰는 게 오프셋(offset)이다. ID 순으로 줄을 세웠을 때 앞에서 몇 개를 건너뛸지 나타내는 값이다.

ID 상품 가격 상태
101 구멍찌 0호 8,000원 판매 중
102 낚시용 핀온릴 5,000원 판매 종료
103 카본 목줄 1.5호 12,000원 판매 중
104 접이식 두레박 9,000원 판매 중
105 바늘 빼기 3,000원 판매 중

판매가 끝난 핀온릴은 조회 대상에서 빠진다. 첫 조회는 구멍찌와 목줄을 가져온다. 다음 조회는 LIMIT 2 OFFSET 2다. 앞의 두 상품을 건너뛰고(OFFSET 2), 거기서 최대 두 개를 가져온다(LIMIT 2).

밝은 두 행이 각 조회의 결과다.

Reader에서 페이지 크기를 정했는데 매퍼에도 OFFSET을 써야 할까?

MyBatisPagingItemReader에 pageSize=2를 설정하면 첫 번째 read()에서 구멍찌와 목줄을 함께 조회한다. Step에 바로 돌려주는 건 구멍찌 하나다. 두 번째 호출에는 남겨 둔 목줄을 돌려주고, 세 번째 호출이 와야 다음 페이지를 조회한다.

새 페이지를 읽을 때 Reader는 매퍼에 _pagesize와 _skiprows를 넘긴다. _pagesize는 한 번에 가져올 최대 개수라서 계속 2다. _skiprows는 건너뛸 개수라서 첫 페이지에서는 0, 두 번째 페이지에서는 2가 된다. 페이지 번호를 0부터 세므로 두 번째 페이지에서는 1 × 2 = 2다.

PostgreSQL을 쓰는 매퍼라면 두 값을 아래 쿼리의 마지막 줄에 넣는다.

SELECT id, name, price
FROM product
WHERE status = 'ON_SALE'
ORDER BY id
LIMIT #{_pagesize} OFFSET #{_skiprows}

이 SQL에서 마지막 줄을 빼면 pageSize를 2로 설정했어도 첫 쿼리부터 판매 상품 전체를 조회한다. Reader가 시작 위치를 계산해 줘도 DB가 실제로 어디서부터 읽을지는 매퍼의 SQL이 정한다.

네 상품을 읽는 흐름을 그리면 아래와 같다. 두 번째와 네 번째 호출에서는 화살표가 DB까지 가지 않는다.

첫 페이지를 읽고 나서 구멍찌 판매가 끝나면?

여기까지는 두 번 조회하는 동안 같은 상품 네 개가 보였다. 그런데 구멍찌와 목줄을 파일에 쓴 직후 구멍찌 판매가 끝나고, 그 변경이 다음 조회에 반영되면 어떻게 될까?

시점 SQL이 보는 판매 중 상품(ID순) 조회 결과
첫 조회 · OFFSET 0 구멍찌, 목줄, 두레박, 바늘 빼기 구멍찌, 목줄
두 번째 조회 · OFFSET 2 목줄, 두레박, 바늘 빼기 바늘 빼기

두 번째 조회도 앞에서 두 개를 건너뛴다. 그런데 이제 앞의 두 개는 목줄과 두레박이다. 두레박은 여전히 판매 중인데 CSV에는 실리지 않는다.

마지막 100개를 읽기까지

판매 상품이 밤새 하나도 바뀌지 않아도 뒤쪽 조회는 느려질 수 있다. 10만 개를 100개씩 읽는 배치에서 첫 100개와 마지막 100개를 가져오는 쿼리를 비교해 보자.

-- 첫 100개
LIMIT 100 OFFSET 0

-- 마지막 100개
LIMIT 100 OFFSET 99900

Reader가 받는 건 어느 쪽이든 100개다. 그런데 마지막 100개를 가져오는 쿼리는 판매 상품을 ID 순서로 99,900개 건너뛴 다음에야 결과를 돌려준다. 앞 페이지들을 CSV에 다 써 뒀어도 DB는 이번 쿼리에서 그만큼을 다시 지나가야 한다.

그래서 한 번에 읽는 양은 100개로 두고 다음 페이지를 찾는 방법을 바꿨다. 첫 100개는 전처럼 ID 순서로 읽는다. 기본 Reader가 넘겨주는 _skiprows 대신, 마지막 상품의 ID를 기억해 뒀다가 다음 조회 때 매퍼에 lastId로 전달하도록 읽기 로직을 바꿨다.

SELECT id, name, price
FROM product
WHERE status = 'ON_SALE'
  AND id > #{lastId}
ORDER BY id
LIMIT 100

이렇게 마지막으로 읽은 값을 다음 조회의 기준으로 삼는 방식을 키셋 페이징이라고 한다. 판매 상태와 ID 순서에 맞는 인덱스가 있으면 DB는 마지막 ID 다음부터 읽을 수 있다.

마치며

처음에는 한 번에 100개씩 읽으니 첫 페이지나 마지막 페이지나 DB가 하는 일도 비슷할 줄 알았다. 그런데 pageSize가 같아도 마지막 조회에는 OFFSET 99900이 붙었다. 100개씩 읽는 설정은 그대로 뒀다. 매퍼에 마지막 상품 ID를 넘기자, 뒤쪽 페이지에서도 앞에 몇 개가 있었는지 다시 셀 필요가 없어졌다.
