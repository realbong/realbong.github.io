상품을 100개씩 읽고 10개씩 커밋하면, DB 연결도 10개마다 닫힐까?

realbong2024.06.23수정 2026.11.19
spring-batchmybatispostgresql

fetchSize와 청크 크기가 바꾸는 DB 왕복, 커밋 횟수와 커서 연결 수명을 비교한다.

목차

  • 10만 개를 더 빨리 내보내려면 어느 숫자를 바꿔야 할까?
  • 마치며
  • 레퍼런스

낚시용품 쇼핑몰에서 가격비교 사이트에 보낼 상품 목록을 만든다. Spring Batch의 Reader가 DB에서 판매 중인 상품 10만 개를 읽고, Writer가 상품명과 가격을 CSV 파일에 한 줄씩 쓴다. 코드를 보면 상품을 몇 개씩 다룰지 정하는 숫자가 두 곳에 있다. MyBatis 매퍼의 fetchSize는 100이고, Step의 청크 크기는 10이다. 열 개를 쓰고 커밋한 직후가 궁금했다. 11번째 상품은 이미 받아 둔 90개에서 꺼낼까, DB에 다시 요청할까?

먼저 100은 조회하는 쪽의 설정이다. 여기서 쓰는 MyBatisCursorItemReader는 아래 SELECT를 한 번 실행하고, 열린 조회 결과에서 상품을 하나씩 꺼내 주는 MyBatis-Spring의 Reader다. 예제에서는 Reader가 사용하는 연결의 자동 커밋을 끄고 결과를 앞으로만 읽는다. 이 조건에서 PostgreSQL JDBC 드라이버는 fetchSize에 맞춰 행을 나눠 받는다.

<select id="selectOnSale" resultType="example.Product"
        fetchSize="100" resultSetType="FORWARD_ONLY">
  SELECT id, name, price
  FROM product
  WHERE status = 'ON_SALE'
  ORDER BY id
</select>

Step이 한 트랜잭션에서 처리하는 상품 묶음을 **청크(chunk)**라고 한다. 여기서 10은 그 묶음에 들어가는 상품 수다. 아래 Step은 Reader에서 상품을 하나씩 꺼낸다. 열 개가 모이면 Writer에 넘기고, 쓰기에 성공하면 그 청크를 커밋한다.

return new StepBuilder("exportProducts", jobRepository)
        .<Product, Product>chunk(10, transactionManager)
        .reader(productReader)
        .writer(csvWriter)
        .build();

11번째 상품에서 다시 SELECT를 실행할까?

MyBatisCursorItemReader는 Step을 열 때 조회 전용 DB 연결을 얻고 커서를 연다. 이 연결은 청크의 트랜잭션에 참여하지 않는다. 그래서 첫 청크가 커밋된 뒤에도 Reader는 같은 커서에서 11번째 상품을 꺼낼 수 있다.

Reader / JDBC                      Step / Writer
     |                                  |
     | open cursor, fetch 1..100        |
     |----  1..10 --------------------->| write 10, commit
     |---- 11..20 --------------------->| write 10, commit
     :                                  :
     |---- 91..100 -------------------->| write 10, commit
     |                                  |
     | fetch 101..200 (same cursor)     |
     |---- 101..110 ------------------->| write 10, commit
     :                                  :
     | close cursor at end of step      |

화살표 하나는 read() 열 번을 묶어 그린 것이다. 숫자는 상품을 읽은 순번이다. 11번째에는 새 청크가 시작되지만 상품은 이미 드라이버에 있다. 101번째가 되어야 드라이버가 DB에서 다음 100행을 받아 온다. 이때 DB와 통신은 한 번 더 해도 처음 실행한 SELECT의 결과를 이어 읽는다.

10만 개를 더 빨리 내보내려면 어느 숫자를 바꿔야 할까?

상품 10만 개를 CSV로 끝까지 내보낼 때 두 설정을 하나씩만 바꾸면 횟수가 어떻게 달라질까? 아래 숫자는 설정값으로 계산한 횟수다. 필터링이나 재시도는 없다고 가정했다. 상품이 들어 있는 묶음만 센 값이므로, 마지막에 결과가 끝났는지 확인하는 통신이나 커밋은 표에 포함하지 않았다.

설정 DB에서 받아 오는 상품 묶음 Writer에 넘기고 커밋하는 묶음
기준 · fetchSize=100, chunk=10 1,000번 10,000번
읽는 양만 늘림 · fetchSize=500, chunk=10 200번 10,000번
청크만 키움 · fetchSize=100, chunk=100 1,000번 1,000번

DB에서 다음 묶음이 오기를 기다리는 시간이 길다면 첫 번째로 바꿔 볼 값은 fetchSize다. 500행씩 받으면 같은 SELECT의 결과를 더 적은 횟수에 걸쳐 가져온다. 대신 드라이버가 한 번에 보관하는 행이 많아진다. 상품 설명처럼 긴 문자열까지 읽는다면 이 차이가 메모리 사용량에 나타날 수 있다.

Writer 호출과 커밋에 시간이 많이 든다면 청크 크기가 더 직접적이다. 10개에서 100개로 키우면 상품을 담은 청크의 커밋 횟수는 10분의 1로 줄어든다. 그래도 CSV에는 똑같이 10만 줄을 써야 한다. 파일 쓰기 자체가 오래 걸린다면 전체 시간까지 10분의 1이 되지는 않는다. 또 한 청크를 모으는 동안 메모리에 들고 있는 상품이 늘고, 실패한 청크를 다시 처리할 때 범위도 커진다.

마치며

11번째 상품을 읽을 때 새로 시작되는 건 청크다. 커서는 그대로 열려 있다. 청크를 줄이면 Writer가 더 자주 쓰고 커밋할 뿐, 조회 연결은 여전히 Step이 끝나 Reader를 닫을 때 반환된다.
